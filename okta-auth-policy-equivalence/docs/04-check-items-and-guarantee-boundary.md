# 04. チェック項目一覧と「担保境界」

**目的**：Terraform 版ポリシーを **本番環境のサインインに影響を与えずに** 適用したい。
そのために「何を・どの手段で確認するか」を列挙し、
**静的（apply 前・本番無影響）に担保できる範囲** と
**実際に適用してみないと分からない範囲** の境界を明示する。

---

## 4.0 まず結論（担保境界の全体像）

```
  ┌─ 静的に担保（apply 前・本番ゼロ影響）─────────────┐
  │  L1 構造等価： golden_old(凍結) vs planned_new(plan.json)  │
  │  → 設定（ルール列・条件・action・認証要件・Catch-all 変換）が   │
  │    変換 T の通りか、INV-1 / INV-2 を満たすかを網羅的に検証      │
  └────────────────────────────────────────────┘
                       │ ここまでは本番に一切触れない
  ┌─ 本番無影響だが「実テナント」が要る ───────────────┐
  │  L2 挙動等価： 新ポリシーを **アプリ未割当のまま作成** し、       │
  │    Policy Simulation API（read-only）で代表シナリオを評価        │
  │  → 評価エンジンの実挙動・参照エンティティ解決を裏取り（代表点）   │
  └────────────────────────────────────────────┘
                       │ ここまで本番サインインは旧ポリシーのまま
  ┌─ 実適用しないと分からない（＝本番影響が出る瞬間）──────┐
  │  カットオーバー： 対象アプリの割当を旧→新へ切替           │
  │  → 実トラフィックでの最終確認。観測期間で Deny 急増等を監視     │
  └────────────────────────────────────────────┘
```

**鍵となる事実**：新ポリシーは **作成しただけでは本番に影響しない**。
影響が出るのは「**アプリへの割当（mapping）を切り替えた瞬間**」だけ。
よって `L1`（plan ベース・完全静的）＋ `L2`（未割当ポリシーへの read-only Simulation）まで
**本番無影響で**到達でき、残る不確実性をアプリ割当の前にほぼ潰せる。

---

## 4.1 静的に担保できる項目（apply 前 / 本番ゼロ影響）

`terraform plan -json` から起こした `planned_new` を、凍結済み `golden_old` と L1 比較する。
実テナントへの書き込みは無く、**本番のサインイン判定には一切触れない**。

| # | チェック項目 | 検証手段 | 網羅性 |
|---|--------------|----------|--------|
| S1 | 明示ルールの **本数** が一致（Catch-all 変換分の差のみ許容） | `diff_policies` rule_count | 完全 |
| S2 | 明示ルールの **順序（相対 priority）** が一致 | `test_explicit_rules_preserved_in_order` | 完全 |
| S3 | 各ルールの **conditions** が完全一致（network/zone, user/group, userType, device managed/registered/assurance, platform, risk, elCondition） | `_rule_diffs` conditions | 完全（設定値レベル） |
| S4 | 各ルールの **access（ALLOW/DENY）** が一致 | `_rule_diffs` access | 完全 |
| S5 | 各ルールの **認証要件**（factorMode, constraints, reauthenticateIn, inactivityPeriod, type, その他取りこぼしキー）が一致 | `_rule_diffs` requirements | 完全（設定値レベル） |
| S6 | **Catch-all 変換 T** の構造一致：旧 Deny→追加なし／旧 Allow→末尾に「ANY＋旧要件の ALLOW」＋ system Deny | `diff_policies` = `T(old)` vs new | 完全 |
| S7 | **INV-1**：カスタム Catch-all の conditions が完全に無条件（ANY） | `assert_inv1` | 完全 |
| S8 | **INV-2**：カスタム Catch-all の ALLOW が認証要件を伴い（≠ ANY ALLOW）旧と一致 | `assert_inv1` | 完全 |
| S9 | **system 既定 Catch-all が DENY**（フェイルセーフ健在） | `assert_inv1` | 完全 |

→ **「設定（テキスト）としての同一性」はここで網羅的に確定する。** 本番影響ゼロ。

---

## 4.2 実適用（実テナント）しないと分からない項目

設定が一致していても、**実際の評価結果が一致するか**は別問題。以下は
「同一テナント上に実体を持って初めて」確認できる。多くは **staging org または
未割当ポリシーへの read-only Simulation** で、本番影響を出さずに前倒しできる（4.3）。

| # | チェック項目 | なぜ静的に担保できないか | 確認手段 | 残リスク |
|---|--------------|--------------------------|----------|----------|
| D1 | **参照エンティティの同一性**（network zone / group / device assurance policy / IdP の各 ID が、旧と新で「同じ実体・同じ意味」を指すか） | 構造比較は ID 文字列の一致しか見ない。Terraform import の ID マッピング次第で、同名でも別実体を指し得る | Simulation 結果（zone/group 判定）の突合 / import マッピングのレビュー | 中 |
| D2 | **matches() の実解釈**（評価エンジンが各条件をどう判定・短絡するか。特に zone の実 IP マッピング、device assurance の充足判定、elCondition の式評価） | 仕様＝実挙動とは限らず、設定値からは導けない | L2 Simulation（境界値・witness シナリオ） | 中 |
| D3 | **優先度の実評価順序**（Terraform が振る priority 絶対値で、意図通りの順に評価されるか） | priority 絶対値は正規化で捨てており、実順序は実体依存 | L2 Simulation（順序が効くシナリオ） / live state の priority 確認 | 低〜中 |
| D4 | **Catch-all 変換 T の挙動保存性の実証**（fall-through が本当にカスタム ALLOW に落ち、system Deny に漏れないか） | INV-1/2 は静的前提。実エンジンでの fall-through 経路は実測が要る | L2 fall-through シナリオ＋「system Deny ヒット数 = 0」監視 | 低（INV で強く拘束済み） |
| D5 | **認証要件の実発火**（factorMode/constraints が実サインインで意図通りの factor を要求するか） | 設定一致と、実際に要求される factor が同じかは別 | L2 Simulation の requirements 突合 / 限定ユーザでの実サインイン | 中 |
| D6 | **アプリ割当（mapping）の切替**＝本番サインインがどのポリシーで判定されるか | これはポリシー *内容* と別レイヤ。割当変更そのものが本番への適用 | カットオーバー（限定割当→本割当）と観測 | **高（唯一の不可避な本番操作）** |
| D7 | **Okta 側の経時的仕様変更**（platform 判定や factor 仕様の変化） | 将来事象は事前検証不能 | L2 の定期実行・ドリフト監視（runbook 3.4/3.7） | 継続監視 |

## 4.3 「本番無影響」を最大化する適用順序

不確実性（4.2）を、**本番サインインに触れる前に**できる限り潰す。

```
[Step 1] plan のみ        : terraform plan -json → L1（S1–S9）。本番ゼロ影響で設定同一性を確定。
[Step 2] 未割当で apply    : 新ポリシーを作成するが **どのアプリにも割り当てない**。
                            本番サインインは引き続き旧ポリシーで判定される＝影響ゼロ。
[Step 3] read-only L2     : 未割当の新ポリシーへ Policy Simulation API（評価のみ・状態変更なし）。
                            D1–D5 を代表点で裏取り。ここまで本番トラフィックは一切動かない。
[Step 4] 限定割当         : テストアプリ/テストユーザにのみ新ポリシーを割当て実サインイン確認（D6 の一部）。
[Step 5] 本割当（cutover）: 対象アプリを新ポリシーへ。旧は温存（即ロールバック用）。← ここが唯一の本番適用。
[Step 6] 観測             : N 日 green を継続。Deny 急増 / system Deny ヒット>0 を監視（D4/D6/D7）。
```

- **Step 1–3 は本番無影響**で、D6 を除く不確実性をほぼ解消できる。
- **本質的に「適用してみないと分からない」のは Step 5（アプリ割当の切替）だけ**であり、
  そこも限定割当（Step 4）と即時ロールバック（旧温存）でリスクを段階化する。

---

## 4.4 まとめ：担保できること / できないこと

- **担保できる（静的・本番ゼロ影響）**：
  ルール列・条件・action・認証要件・Catch-all 変換・INV-1/INV-2・フェイルセーフという
  **「設定の同一性」** は、apply 前に L1 で **網羅的** に確定する。
- **実テナントが要るが本番無影響に前倒しできる**：
  参照エンティティ解決・matches() 実解釈・優先度実順序・要件の実発火という
  **「実評価結果の同一性」** は、未割当ポリシーへの read-only Simulation（L2）で代表点を裏取り。
- **適用してみないと分からない（唯一の不可避な本番操作）**：
  **アプリ割当の切替（カットオーバー）** と、その後の実トラフィック観測・Okta 仕様の経時変化。
  ここは限定割当・旧温存・観測期間で段階的に担保する。
